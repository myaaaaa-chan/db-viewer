# 設計判断の記録ルール（documentation-and-adrs スキル）

**設計判断をしたら、コードだけ残して終わりにしない。** なぜそう決めたか・何を捨てたかは
コードから読み取れない。記録には `documentation-and-adrs` スキルを使う。

## スキルを呼ぶとき

以下に当たったら、実装に入る前に `Skill(documentation-and-adrs)` を呼ぶ。

| 場面 | 例 |
| --- | --- |
| 構成を変える判断 | ライブラリ・外部サービス・モデルの選択、同期処理かジョブキューか |
| 境界の取り決めを変える | API のリクエスト・レスポンスの形、ファイル形式、DB スキーマ |
| 実測して数値が動いた | 応答時間・料金・上限・しきい値 |
| 運用手順が増減した | 環境構築の手順、ビルド・起動の前提 |
| 同じ説明を 2 回した | 口頭・チャットで繰り返し説明した内容 |

**呼ばなくてよいもの:** 表示の微調整、ログ文言、リファクタ、既存の決定に沿った実装。

## 置き場所（スキルの既定を上書きする）

スキルは既定で `docs/decisions/` に `ADR-001-…`（英語）を作ろうとするが、**使わない。**

| 内容 | 置き場所 |
| --- | --- |
| 設計判断の決定 | `docs/adr/NNN-<日本語のトピック名>.md`（一覧は `docs/adr/README.md`。無ければ最初の 1 本と一緒に作る） |
| 元になった仕様・調査 | `docs/仕様/` |
| 機能単位の設計・測定 | `docs/設計/<機能名>/` |
| ビルド・起動・手元で動かす手順 | Web アプリのルートの `README.md` |

- **番号は決めた順**（`001-` から）
- **役目を終えた文書は `docs/設計/old/` へ移す。** 消さない。**新しいものを old/ に作らない**

## 文書の形

**結論を先頭に置く。**

```markdown
# <トピック> — <一行で何をするか>

<なぜ要るのか。症状か制約を 2〜3 行で。>

**結論を先に:**

| 論点 | 決定 |
| --- | --- |
| <決めたこと> | **<決めた内容>。**<一行の理由>★ |

---

## 1. なぜ要るのか
## 2. 決めたこと
## 3. 捨てた案と理由
```

- **捨てた案を必ず書く。** 半年後に同じ議論をやり直さないために書いている
- 決定は太字で言い切る。「〜が望ましい」で終わらせない

## 数値の扱い

**設計文書・手順書に書く数値は実測したものだけ。**

- 実測値には **★** を付け、出典（測定ファイル・ログ・章番号）を併記する
- 実測でないものは **「未計測」と明記する。** 書かずに載せない。
  **これからどうなるかを言うときは「予想」**（月の料金・上限に達する時期など）
- 料金・負荷を、利用量に比例する仮定だけで出さない

## 決定を変えるとき

- **古い文書を消さない。** 経緯が消える
- **ADR は動かさない。** 古い ADR の冒頭に `> ★ **状態: …**——何が変わったか` を書き、`docs/adr/README.md` の「状態」の列を直す（場所を動かすとリンクが壊れる）
- 設計文書（`docs/設計/`）は役目を終えたら `old/` へ移す
- 差し替えるときは新しい文書に「いつ・何が変わったか」を書き、古い方から参照させる

## README への反映

以下が出たら Web アプリの `README.md` に 1〜2 行で足す。**罠は入口に置かないと踏む。**

- 新しい罠（ビルドは通るが実行時に壊れる類。ブラウザの権限・HTTPS 必須・ブラウザごとの対応差など）
- 料金・上限など、判断の前提になる実測値
- 手順の増減

## 禁止事項

- API キー・`.env*` の中身を文書に書くこと
- スキルのテンプレート（英語・`ADR-001`・`docs/decisions/`）をそのまま持ち込むこと
- コードを読めば分かることを文書化すること（*何を*ではなく*なぜ*を書く）
- 「後でドキュメントを書く」という判断（実装と同じ変更に含める）
- 実測していない数値を、実測のように書くこと
